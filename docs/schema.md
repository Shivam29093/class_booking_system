# Schema

The application uses PostgreSQL with SQLAlchemy models. Primary keys are PostgreSQL UUIDs generated by the application. Timestamps use timezone-aware `DateTime` columns. Status/role values are stored as strings and constrained by application enums.

## Tables

### `users`

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `email` | VARCHAR(255) | Required, unique, indexed |
| `password_hash` | VARCHAR(255) | Required |
| `role` | VARCHAR(20) | Required; `STAFF` or `INSTRUCTOR` |
| `created_at` | TIMESTAMPTZ | Required |

### `instructors`

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `user_id` | UUID | Required, unique FK to `users.id` |
| `name` | VARCHAR(150) | Required |

An instructor has a one-to-one relationship with a user account.

### `members`

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `name` | VARCHAR(150) | Required |
| `email` | VARCHAR(255) | Required, unique, indexed |
| `membership_expiry` | DATE | Required |
| `created_at` | TIMESTAMPTZ | Required |
| `updated_at` | TIMESTAMPTZ | Required |

The deployed application also tracks membership-alert dismissal state so a dismissed alert can reappear when the expiry date is subsequently moved to a new/later date that again enters the alert window.

### `rooms`

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `name` | VARCHAR(100) | Required, unique |

### `classes`

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `title` | VARCHAR(150) | Required |
| `description` | TEXT | Required |
| `discipline` | VARCHAR(100) | Required |
| `default_duration_minutes` | INTEGER | Required |
| `default_capacity` | INTEGER | Required |
| `is_archived` | BOOLEAN | Required, default false |
| `created_at` | TIMESTAMPTZ | Required |
| `updated_at` | TIMESTAMPTZ | Required |

### `sessions`

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `class_id` | UUID | Required FK to `classes.id`, indexed |
| `session_date` | DATE | Required, indexed |
| `start_time` | TIME | Required |
| `primary_instructor_id` | UUID | Required FK to `instructors.id` |
| `room_id` | UUID | Required FK to `rooms.id` |
| `duration_minutes` | INTEGER | Required |
| `capacity` | INTEGER | Required |
| `created_at` | TIMESTAMPTZ | Required |
| `updated_at` | TIMESTAMPTZ | Required |

### `session_instructors`

This is the many-to-many join table for co-instructors.

| Column | Type | Constraints |
|---|---|---|
| `session_id` | UUID | FK to `sessions.id`, part of composite primary key |
| `instructor_id` | UUID | FK to `instructors.id`, part of composite primary key |

### `bookings`

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `session_id` | UUID | Required FK to `sessions.id`, indexed |
| `member_id` | UUID | Required FK to `members.id`, indexed |
| `status` | VARCHAR(20) | Required, indexed |
| `booked_at` | TIMESTAMPTZ | Required |
| `updated_at` | TIMESTAMPTZ | Required |

A database `UNIQUE(session_id, member_id)` constraint guarantees one booking row per member/session.

### `booking_history`

| Column | Type | Constraints |
|---|---|---|
| `id` | UUID | Primary key |
| `booking_id` | UUID | Required FK to `bookings.id`, indexed |
| `event_type` | VARCHAR(20) | Required |
| `old_status` | VARCHAR(20) | Nullable |
| `new_status` | VARCHAR(20) | Nullable |
| `note` | TEXT | Nullable |
| `changed_by_user_id` | UUID | Nullable FK to `users.id` |
| `created_at` | TIMESTAMPTZ | Required, indexed |

ORM event listeners reject both updates and deletes on history rows, making the timeline append-only from the application's perspective.

## Relationships

- `users` → `instructors`: one-to-one.
- `classes` → `sessions`: one-to-many.
- `instructors` → primary `sessions`: one-to-many.
- `rooms` → `sessions`: one-to-many.
- `sessions` ↔ `instructors`: many-to-many through `session_instructors` for co-instructors.
- `members` → `bookings`: one-to-many.
- `sessions` → `bookings`: one-to-many.
- `bookings` → `booking_history`: one-to-many.
- `users` → `booking_history`: one-to-many through `changed_by_user_id`.

## Database constraints vs application rules

The database handles structural integrity: primary keys, foreign keys, uniqueness, required fields and the unique member/session booking constraint. PostgreSQL is also used transactionally when booking logic locks rows.

The application handles rules that depend on current state or business meaning: membership expiry, whether a session has started, capacity calculation, booking status transitions, waitlist ordering/promotion, attendance timing, role authorization, instructor visibility, schedule overlap checks and alert dismissal/reappearance.

That split keeps relational integrity close to the data while keeping business policy explicit in the service/API layer.

## Deliberate denormalisation

There is little deliberate denormalisation. Session duration and capacity are stored on the session even though they default from the class because sessions are historical/scheduled instances and can override those defaults independently. Keeping those values on the session avoids having past sessions change when a class default is edited.

## What breaks first at 100x the data

The first pressure points would be list/report queries and the recurring/dashboard aggregation paths rather than basic CRUD. Booking search would need careful composite indexes for the requested filters/sorts, and reporting would likely benefit from pre-aggregation or materialized reporting data. Connection pooling, pagination limits, and background jobs would also become more important. The current design already avoids loading every booking into the browser and uses indexed foreign keys/status/date fields for the core queries.
